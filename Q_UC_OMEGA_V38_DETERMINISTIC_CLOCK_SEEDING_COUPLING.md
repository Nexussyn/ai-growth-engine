# Q-UC Ω V38 — Deterministic Clock-Seeding Coupling in AMP4-TPP

Date: 2026-09-18
Status: verified code-level finding; causal historical effect NOT yet established.

## Executive finding

A code-level defect was identified in the public AMP4-TPP implementation that is stronger than the previously noted Math.random()/Alea discrepancy.

The vendored Alea implementation is exact and its no-argument constructor seeds itself from the current millisecond clock:

    if (args.length == 0) {
        args = [+new Date];
    }

The experimental backend defines:

    const generate = () => new Alea()();
    const coinFlip = () => generate() >= 0.5;

and the target is generated inside:

    app.get('/ping/:erotic/:nonErotic', ...)
        -> user.getUser(...)

Therefore the target side is not generated by a persistent PRNG state. It is:

    T_i = 1{ f(floor(t_i_ms)) >= 1/2 }

where f is the deterministic first-output map of Alea and t_i_ms is the server request time.

This is a mathematical identity for the published code path.

## Stronger coupling

The same getUser() call performs several independent-looking random calls by repeatedly constructing a fresh Alea instance.

Thus, if two calls occur in the same millisecond:

    new Alea()  -> seed = t
    new Alea()  -> seed = t

and because Alea is deterministic for a fixed seed:

    output_1 = output_2

exactly.

The first code-level call in getUser() is a coin flip for picType; a later call is a coin flip for side. Hence, whenever those two calls fall in the same millisecond:

    picType == side

with probability exactly 1.

This coupling is not a statistical approximation. It follows directly from deterministic seeded PRNG construction.

## Exact local replay benchmark

The vendored Alea source from the repository was reproduced byte-for-byte at the algorithmic level and the getUser-like call pattern was benchmarked under Node.js 22.

For 1,000,000 repetitions of:

    coinFlip()
    generate()
    coinFlip()

the two coin flips agreed in:

    999,043 / 1,000,000 = 99.9043%

This number is an implementation benchmark, not a historical estimate of the original deployment.

A second benchmark of two consecutive coinFlip() calls gave:

    999,512 / 1,000,000 = 99.9512%

Again, this demonstrates execution-time collision under a modern runtime; it does not prove the exact historical collision rate.

## More important consequence for the actual target

The target side is generated AFTER the participant's guess reaches the server.

Let:

    G_i = participant's pre-request guess
    A_i = request arrival time
    T_i = target side generated by the server

The intended design requires approximately:

    T_i independent of G_i and of the participant's conventional state,

conditional on everything before the target draw.

But the implementation gives:

    T_i = f(A_i).

If the participant's action, reaction time, network path, or other state changes A_i, then there is a causal path:

    participant state
          |
          v
    response timing
          |
          v
    server millisecond A_i
          |
          v
       T_i = f(A_i)

This is an ordinary causal timing channel. No precognition is required.

## Important empirical property of the deterministic clock map

For 200,000 consecutive millisecond seeds, direct reconstruction of f(t) gave:

- mean target probability: 0.500685
- one-step flip probability: 0.503493
- one-step same probability: 0.496507

Thus the map does not behave like a smooth deterministic bias that can simply be dismissed as a constant left/right imbalance.

Instead it behaves approximately like a deterministic high-frequency binary code indexed by the server clock.

This makes the timing channel more subtle:

    absolute/arrival time -> deterministic bit

rather than:

    time -> slowly drifting target bias.

## 1-second scale

In the same 200,000-ms reconstruction, 1,000-ms windows had target proportions ranging approximately from 0.46 to 0.55.

Therefore a process that systematically samples particular temporal subwindows could experience nontrivial conditional target imbalance even though the unconditional target sequence is nearly 50/50.

This is a key distinction:

    P(T=1) ≈ 0.5

does NOT imply:

    P(T=1 | timing/latency state) = 0.5.

## Why this can specifically matter to AMP-TPP

The published paper states that the target side was randomly determined by the computer after the participant's guess and that the target randomization was intended to be independent. It also states that Alea was used for all randomization steps.

The public implementation instead reconstructs a fresh Alea from the millisecond clock for each random call.

The paper reports:

- Study 1 erotic pure-session: 49.48%
- Study 2 erotic: 49.65%
- Study 3 erotic: 50.07%

and reports null results for the REG-based counterfactual experiments, while the participant-based Study 2 produced the below-chance result.

This pattern is compatible with, but does not establish, a participant-timing mechanism: the human and REG pipelines can have different latency distributions.

## Mathematical falsification criterion

Let C_i be a pre-registered timing covariate measured independently of the participant's semantic response, for example server request timestamp modulo a fixed interval or latency bucket.

The ordinary randomization claim requires:

    H0: I(T; C | X) = 0

where X contains all prerequest experimental state.

The code predicts a stronger structural relation:

    H(T | A_ms) = 0

up to implementation/runtime uncertainty, because T is a deterministic function of the millisecond seed.

This is fundamentally different from a genuine external random source, for which:

    H(T | A_ms) > 0

unless the source is otherwise compromised.

Therefore this is directly testable from archived timestamps.

## Decisive historical test

For every archived trial with a trustworthy server timestamp:

1. reconstruct the millisecond timestamp;
2. implement the exact vendored Alea 0.9 function;
3. compute f(timestamp);
4. compare predicted target side with recorded target_side;
5. measure exact accuracy;
6. test timestamp rounding uncertainty ±1, ±2, ±5, ±10 ms;
7. compare human trials against REG trials;
8. estimate I(T; timestamp);
9. test I(T; timestamp | condition, participant, session);
10. test response latency -> timestamp -> target mediation.

A match materially above 50% would constitute a direct reconstruction of the target generator.

A failure to match would identify either a deployment/version mismatch or a timestamp transformation not represented in the public source.

## Critical limitation

The current result is NOT evidence that the historical Study 2 anomaly was caused by this mechanism.

The raw trial-level server timestamps have not yet been reconstructed in this environment. The benchmark above uses the public implementation and a modern Node runtime.

The strongest current claim is therefore:

> The public AMP4-TPP implementation defines the target through a deterministic function of the server millisecond clock, rather than through a persistent random state. This creates a formally demonstrable timing-to-target channel that must be eliminated before interpreting the human-vs-future-target result as anomalous.
